# 项目重构与保存复现机制探讨任务

在日渐的科研项目开发过程(AnyRotate)中，我发现了一些弊病，它使得一些日常操作非常不顺心，譬如我过去训练的效果很不错的一个模型（.pth)，过了几个月后，因为AnyRotate/source/leaphand/leaphand/tasks/manager_based/leaphand/inhand_base_env_cfg.py的某些改动，特别是观察项的变动，导致我无法复现之前的训练结果，每次回溯、修改都特别麻烦，要么重训，但结果发现效果不如之前，这就很令人绝望，需要排查。所以这个问题机制需要探讨一下，是用git管理工具来确保可靠的复现机制（每当一个效果不错的模型训练好后），还是用更新且鲁棒的任务环境组织架构来管理？（这个和第二个弊病也有点联系）；

还有一个弊病是，AnyRotate/source/leaphand/leaphand/tasks/manager_based/leaphand下的环境任务文件越来越繁杂，inhand_base_env_cfg.py是一个基础配置的文件，许多其他任务文件都基于它进行修改和扩展，但是随着时间的推移，越来越多的任务文件被创建出来，导致管理和维护变得困难，inhand_base_env_cfg.py牵一发而动全身。
我看了下IsaacLab/source/isaaclab_tasks/isaaclab_tasks/manager_based/manipulation/inhand的组织架构设计，可能更合理一些。我这个目前是一个env_cfg对应一个具体的环境任务，它那个组织结构似乎更模块化和解耦。体感上可能更符合软件工程的设计原则。

还有一个细枝末节，命名修改：AnyRotate -> AnyMani，同理包括各个leaphand目录，leaphand是灵巧手，但AnyRotate项目未来可能不止灵巧手，还会有其他机械手，所以命名上更通用一些。AnyRotate/source/leaphand/leaphand/tasks/manager_based/leaphand这种就不合适了，这点我觉得同样可以借鉴Isaaclab，看它们是怎么做到的。

有一个背景，就是这里的环境任务基本是RL任务，我后续有一个大体的科研idea就是用RL训练好的策略蒸馏数据，然后会用来做模仿学习训练更通用和泛化的策略，这也是为什么我有时想要去重新跑一下过去训练的效果很不错的模型。这个和本次任务可能没有直接联系，但也需要你注意一下。

我打算先创建一个分支进行重构工作，等到这里稳定之后，再合并回main
